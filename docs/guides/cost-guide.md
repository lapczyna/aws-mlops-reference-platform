# Cost Guide

## TL;DR

At demo/reference volumes, this platform costs roughly **$1-2/month**, and
the dominant line item at any volume is **SageMaker Batch Transform
instance time**, not the serverless request-based services. Reproduce or
adjust every number below with:

```bash
python scripts/estimate_cost.py --jobs-per-month 1000
```

## Worked estimates

Generated by `scripts/estimate_cost.py` with its documented assumptions
(5 API requests/job, 5 Lambda invocations/job, a 4-minute `ml.m5.large`
Batch Transform job per submission, US East (N. Virginia) on-demand list
pricing, no free tier or committed-use discounts applied):

| Service                     | 100 jobs/mo | 1,000 jobs/mo | 10,000 jobs/mo |
| ------------------------------ | -------------: | ----------------: | -----------------: |
| API Gateway                     | $0.0018        | $0.0175           | $0.1750            |
| Lambda                          | $0.0006        | $0.0060           | $0.0600            |
| Step Functions                  | $0.0125        | $0.1250           | $1.2500            |
| **SageMaker Batch Transform**      | **$0.7667**    | **$7.6667**       | **$76.6667**       |
| DynamoDB                         | $0.0004        | $0.0043           | $0.0425            |
| CloudWatch (6 alarms + logs)       | $0.6025        | $0.6250           | $0.8500            |
| **Total**                          | **$1.38**      | **$8.44**         | **$79.04**         |

S3 storage/request costs and the optional customer-managed KMS key are
omitted from the script -- both are negligible for small CSV datasets at
these volumes (a few cents a month at most) and are covered qualitatively
below.

**These are planning estimates, not quotes.** Prices change, your dataset
sizes and instance-time-per-job will differ from the assumptions above, and
this document will drift out of date faster than AWS's own pricing pages.
For a real budget decision, use the
[AWS Pricing Calculator](https://calculator.aws) or your account's Cost
Explorer against actual usage.

## Why SageMaker dominates, and what to do about it

Every other service in this architecture is genuinely pay-per-request with
no floor. SageMaker Batch Transform is billed by **instance-time**, and a
transform job has a minimum practical duration (instance startup + model
load + inference + teardown) regardless of how small the dataset is -- so
it's the one place cost scales with *number of jobs*, not just *data
volume*. Levers, in order of impact:

- **`TransformInstanceType`** (template parameter): the default
  `ml.m5.large` is a reasonable general-purpose choice; a smaller instance
  (`ml.m5.large` is already the smallest standard M5) or a compute-optimized
  type could reduce cost further if profiling shows the job is CPU-bound
  and small.
- **Batch jobs, not one-job-per-row.** The architecture already batches an
  entire dataset per Batch Transform job (per
  [ADR-0003](../adr/0003-sagemaker-batch-transform-vs-processing.md)); the
  cost model rewards clients that batch multiple prediction requests into
  one dataset upload rather than submitting many tiny single-row jobs.
- **`TransformInstanceCount`**: only increase this for genuinely large
  datasets that benefit from parallelism -- it multiplies cost linearly and
  the Iris-sized reference workload never needs more than one instance.

## Cost levers by service

| Lever                                | Where                                         | Effect                                                     |
| ---------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| `LogRetentionInDays`                        | `template.yaml` parameter                        | Bounds CloudWatch Logs storage cost; shorter in `dev`, longer in `prod` per `samconfig.toml`. |
| `DatasetRetentionDays` / `ResultsRetentionDays` | `template.yaml` parameters                    | S3 lifecycle expiration bounds storage growth automatically. |
| DynamoDB TTL (`JobTtlDays`)                    | `template.yaml` parameter                       | Job records expire and stop costing anything to store, without a cleanup job. |
| `EnableCustomerManagedKey`                       | `template.yaml` parameter (default `false`)     | Adds ~$1/month per KMS key plus per-request charges when enabled -- see [ADR-0010](../adr/0010-optional-customer-managed-kms-key.md). Off by default specifically to avoid this cost in `dev`. |
| `StateMachineLogLevel`                             | `template.yaml` parameter (default `ERROR`)     | `ALL` increases Step Functions execution log volume/cost; `ERROR` is the cost-conscious default, override for debugging. |
| Architecture: `arm64` (Graviton)                     | `Globals.Function.Architectures` in `template.yaml` | Lower Lambda price-per-GB-second than `x86_64` for these I/O-bound handlers, at effectively zero migration cost since there's no native-dependency concern beyond what `sam build --use-container` already handles. |
| DynamoDB on-demand (not provisioned)                   | `JobsTable` billing mode                          | No idle capacity cost, no capacity planning -- see [ADR-0005](../adr/0005-dynamodb-single-table-job-state.md). |

## Idle cost

With zero jobs submitted in a month: Lambda, API Gateway, Step Functions,
and SageMaker all bill **$0**. The only non-zero idle costs are the fixed
per-month prices for resources that exist regardless of traffic: 6
CloudWatch alarms (~$0.60/month) and negligible S3/DynamoDB storage for
whatever job history hasn't yet expired via TTL/lifecycle rules. This is
the concrete number behind the "near-zero idle cost" claim in
[ADR-0002](../adr/0002-serverless-first-architecture.md).
